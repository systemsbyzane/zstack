# Managing multiple assignments from one home thread

Read when planning substantial work, running several coordinators, or recovering a stalled assignment.

## One user-facing owner, independent assignment owners

The chief owns the user's intent and priority across assignments. Each coordinator owns a complete deliverable, including integration and verification. Split by independent outcomes, not by every command or lifecycle step. Keep runtime, mutable source and private evaluation ownership explicit. Shared global limits apply across assignments; do not invent a per-task worker quota from a past task.

Record the outcome, ordered phases, deliverables, explicit exclusions, environment, current owner and observable progress in a concise assignment tracker. Carry authority and preferences across handoffs. The user should not have to visit child threads, transmit routine results, or repeatedly approve the same work. Ask only for genuinely missing authority, consequential decisions or unavoidable private authentication.

## Measure progress against the finish line

Use completed items, accepted changes, observed behavior and deliverable readiness. A process being alive, a worker returning, or a successful provider response does not prove task completion or correctness. Distinguish last-reported counts from current verification and give the timestamp. Empty acknowledgment turns and repeated inventories are not milestones.

For evaluation work, preserve the requested baseline/fix/benchmark order. Run the requested cohort rather than repeatedly tuning the first example. Record product failures and continue independent cases where safe. Diagnose recurring failures before redesigning. Keep private expected answers and holdouts away from implementation; freeze candidate, prompts, schema, runner and effective configuration before release. Do not tune after reveal and still call the same sample a holdout.

## Recover without changing owners for every error

Use the repository's actual execution path before adding readiness gates; an inline workflow may not require a queue worker. One runtime owner discovers prerequisites, records stable executable paths and reuses installed dependencies, generated artifacts, services and data. Resolve routine imports/configuration in the same outcome rather than returning a new permission request after every attempt.

Repeated failure should change the method or capability, not merely extend the same tiny slice. Prefer a concrete reproduction through the actual production function over source speculation. Verify that reported fixes address observed cases and neighboring counterexamples. Avoid a growing custom parser or telemetry framework when a narrower product fix would satisfy the outcome.

## Evidence that remains meaningful after integration

Keep code identity, effective runtime identity and evidence identity connected. Do not claim an archive was tested when a long-lived worker loaded another checkout. Record missing telemetry honestly; an offline reconstruction is not a captured runtime stage. Preserve original artifacts when correcting a report and publish a versioned reconciliation for conflicting counts.

Distinguish provider execution success, controlled fixtures, offline replay and independently scored accuracy. Report denominators and coverage gaps; do not compare unpaired cohorts as a causal improvement or collapse overlapping symptoms into a composite score. Operator-entered choices and notes are not extracted facts or automatic product features.

Video proves the version and actions actually recorded. A source comparison or API readback may supplement earlier video but cannot become a final-version UI replay. If a PR moves to main after a feature merge, isolate only the enhancement commits, check the focused diff and affected behavior, and retain the original benchmark identity separately from integration validation.

## Deliver, do not remain in preparation

A requested PR includes ordinary commits, push and PR creation subject to repository/host rules. Publish an actual reviewable PR with the report and accessible media, not only a local draft file. State remaining checks/reviews and known defects. Do not merge or deploy without authority. Use supported PR monitoring when requested; no polling loops. User-requested periodic coordinator updates may use supported scheduling without polling running delegates; stop those updates when the requested delivery is handed back or the user cancels.
