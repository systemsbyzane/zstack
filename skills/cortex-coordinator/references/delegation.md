# Delegation and ownership

Use the shared [clear communication contract](../../cortex/references/communication.md). Initial briefs explain outcome, starting point, ownership/authority, acceptance, and return. Follow-ups contain the change, reason, and next action instead of repeating the full assignment. Never concatenate ordinary words or dump accumulated constraints and historical accounting into a prompt.

Use the active host's supported orchestration tools and binding rules. Discover capabilities before dispatch when required. Cortex chief and assignment coordinators run `gpt-6.1-sol` with reasoning effort `low`. Every delegated worker, including implementation, research, testing and review, uses `gpt-6-luna` with reasoning effort `max`. Pass both model and reasoning explicitly in the supported dispatch settings and verify the returned receipt. Do not inherit the coordinator model, lower reasoning, or substitute another model without explicit user approval. If unavailable, report that specific availability blocker; change the method or brief rather than escalating models automatically.

Delegate implementation outcomes with enough authority and context to finish, not tiny commands. State outcome, starting point, owner and authority, acceptance, and return condition in readable language; give exact accessible file/runtime pointers. Follow-ups state only the change and explicitly supersede conflicting instructions. Keep one technical owner for connected work. The coordinator owns scoping, integration, review, verification, and delivery; it may make a small fix for its own review finding, but does not take over product implementation.

At natural boundaries, inspect already available output quietly to confirm owner, runtime/resource, evidence, next milestone, and blocker. Do not interrupt or poll workers for status. Handle routine setup, fixture, command, and formatting recovery with the current owner without READY/release exchanges or chief permission. Coordinate bounded handoffs only for actual high-memory processes: name the owner and release condition, release on exit or failure, and do not retain a silent reservation during recovery. Do not create task-wide slot gates, worker caps, timers, or quotas. Return to Cortex for a meaningful milestone, integrated delivery, material dependency change, or genuine authority/decision/private-authentication blocker; filter internal chatter.

Before merging incoming main, separate authored from incoming changes, preserve ancestry and the combined tree, and run normal hooks. Report each check as passed, failed, or not run. A worker exit is not completion; return the actual PR/head, evidence, checks, and gaps.

Parallelize only independent work. Serialize overlapping files and mutable runtimes. Tool-managed worktree binding is required where the host requires it; do not create shell checkouts and pretend threads are rebound. A path in a brief must be accessible to its worker. Preserve existing changes and credentials privacy.

Use appropriate focused verification. Respect explicit testing preferences; do not invent universal test bans, full-suite gates, time renewals, provider quotas, or review panels. Explicit task hard limits remain binding. A persistent worker may complete setup, implementation, and verification together. Its return contains results, diff/revision, actual checks and evidence, limitations, and any integration needs.

Follow `next` and completion notifications; no task-status polling, sleep loops, or watchdog agents. Cancel replaced/obsolete tasks using supported cancellation and resolve competing ownership before continuing. A fresh delegated review/recheck is a new task when the host requires it. Use native delegation versus T3 delegation according to active host rules, not this document's assumptions.
